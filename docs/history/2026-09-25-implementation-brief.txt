あなたは `keiba-lab` リポジトリの実装担当です。

このプロジェクトは、JRA全レースを対象とした個人用の競馬予想・検証Webアプリです。
単なる予想画面ではなく、

- JRA-VANからのデータ収集
- 時点別Snapshot管理
- 特徴量生成
- 能力・着順確率予測
- 仮想レースSimulation
- 馬券組み合わせ確率
- Odds / EV評価
- 安定 / バランス / 穴狙いの3戦略
- 資金管理
- Walk-forward Backtest
- Logic Explorerによる計算過程の追跡

までを一貫して扱います。

これまでChatGPTとの設計議論でかなり仕様を詰めています。
まずコードを書き始めるのではなく、その設計をリポジトリ内の
「Source of Truth」として整理してください。
その後、その仕様を基準として自律的に実装を進めてください。

==================================================
0. 開発の進め方
==================================================

ユーザーに細かな判断を逐一求めないでください。

合理的に決定できる技術的事項は自分で判断し、
設計 → 実装 → テスト → 修正まで継続してください。

停止してユーザー確認を求めるのは主に、

- JRA-VAN契約・認証
- APIキー・秘密情報
- 外部サービスへのログイン
- 課金
- 重大な仕様変更
- ユーザーの好みでしか決められないUI/UX
- 既存の確定仕様と両立できない重大な設計判断

が必要になった場合です。

作業開始時には、
「今回はどこからどこまで進めるか」を短く示してください。

==================================================
2. プロダクト基本仕様
==================================================

個人利用のWebアプリ。

対象：
JRA全レース。

馬券購入そのものは自動化しない。
最終的な購入はユーザーが手動で行う。

予想更新タイミング：

- 前日
- 発走30分前
- 発走10分前
- 最新Oddsを手入力した場合の即時再計算

能力予測と市場評価は分離する。

「強い馬を予測する処理」と
「現在のOddsで買う価値があるかを判断する処理」を
混ぜてはいけない。

表示戦略：

- 安定
- バランス
- 穴狙い
- 総合推奨

BUYだけでなくSKIPを正式な判断結果として扱う。

「予測自体は可能だが買う価値がない」と
「データ不足等により予測自体の信頼性が低い」
を区別する。

外部データを追加しても、
JRA-VAN単独Baselineを再現可能にする。

==================================================
4. 時点管理・未来情報リーク防止
==================================================

このプロジェクトで最重要の制約。

すべての予測は、その予測時点で実際に利用可能だった情報だけを使う。

最低限データに、

source_timestamp
received_timestamp
effective_from
snapshot_id

等の時刻情報を持たせる。

Feature生成APIは概念的に、

race_id
horse_id
as_of_time
feature_version

を受け取り、
as_of_timeより未来の情報を取得できない構造にする。

データ層は概ね、

raw
↓
normalized
↓
features

に分離する。

履歴更新は原則上書きせず、
イベント・Snapshotとして保存する。

==================================================
5. Walk-forward Backtest
==================================================

これは確定仕様。

最初のテスト年は必ず2022年。

1:
Train 2019–2021
Test 2022

2:
Train 2019–2022
Test 2023

3:
Train 2019–2023
Test 2024

4:
Train 2019–2024
Test 2025

最終運用モデル：
Train 2019–2025

2026年以降：
Live / ongoing validation

各年について必ず、

1. その年の結果をモデルが見ていない状態で予測
2. Prediction / Recommendationを保存
3. 実際の結果・払戻と照合
4. その年の性能を確定
5. その後にのみ、その年を次年度モデルの学習へ追加

という順序にする。

2022を最初から学習データに含めてはいけない。

==================================================
7. Leak Guard
==================================================

最低限以下の自動検査を実装する。

LEAK-001
発走後情報がFeatureに存在
→ FAIL

LEAK-002
2022テストモデルのTraining Setに2022データが存在
→ FAIL

LEAK-003
能力予測モデルに当該レースOddsが入力
→ FAIL

LEAK-004
Recommendation確定前にResult / payoutへアクセス
→ FAIL

VERSION-001
Feature / Model / Logic Version欠落
→ FAIL

1つでもFAILしたBacktest Runは
正式な成績として扱わない。

==================================================
9. Prediction Model
==================================================

最低3系統を比較可能にする。

A. Baseline
単純な基準モデル。

B. Probability Model
CatBoostを第一候補。
LightGBM等との比較可能性を残す。

予測：

win probability
top2 probability
top3 probability

レース内整合性：

sum(win probabilities) = 1

各馬：

win <= top2 <= top3

必要に応じてCalibrationを行う。

C. Ranking Model
レース単位groupによるRanking。

CatBoost Ranking
QuerySoftMax / YetiRank等を候補。

Probability Modelとの比較・不確実性判断に使う。

最初から複雑なEnsembleにしない。

BlendはWalk-forwardで改善が確認できた場合のみ採用。

ニューラルネットは初期版では使わない。

巨大な三連単専用モデルも初期版では作らない。

==================================================
10. Day-of Update Layer
==================================================

当日情報はAbility Modelとは分離されたUpdate Layerとして扱う。

候補：

- weather
- track condition
- scratches
- jockey changes
- body weight / change
- その他当日公開情報

OddsはAbility Modelには入力しない。

OddsはPrediction後のMarket Evaluationにのみ使う。

==================================================
11. Simulation
==================================================

HorsePredictionを使って仮想レースを生成し、

- win
- quinella
- exacta
- wide
- trio
- trifecta

等の組み合わせ確率を推定する。

Simulation回数は固定100,000回にしない。

初期値を設定し、
推定値の収束・精度・処理時間を見ながら
必要に応じて追加Simulationする設計にする。

人間が定義した複雑な展開・脚質ルールは初期版では入れない。

将来、Walk-forwardで改善した場合のみ採用候補とする。

==================================================
13. Betting Strategy
==================================================

3戦略。

安定：
- 単勝・複勝・ワイド・馬連中心
- 的中確率と安定性優先
- 少ない買い目
- 不確実性が高ければSKIP
- 初期1レース上限：資金の2%

バランス：
- 全券種候補
- 的中率 / EV / payout / 点数を総合
- 初期1レース上限：3%

穴狙い：
- 高配当でも正EVのみ
- 三連複・三連単等も候補
- 少額
- 初期1レース上限：1.5%

これらの%は最終最適値ではない。
安全側の初期値。

2022–2024で検証・調整し、
2025 Test前に固定する。

==================================================
14. Money Management
==================================================

基本：

1/4 Kelly

その後、

- strategy cap
- race cap
- 100円単位
- correlation / overlap control
- model disagreement adjustment
- unsettled exposure limit

を適用する。

最低購入額100円で適切なSizingができない場合はSKIP。

結果未確定馬券の総Exposureは、
初期値として利用可能資金の10%まで。

Daily Budgetは
「その日の総購入額」ではなく
「許容する確定損失」として扱う。

払戻は後続レースに再利用可能。

未確定馬券は別管理。

確定損失がDaily Budgetへ到達したら停止。

負けを取り戻すための追い賭けは禁止。

上限を増やす場合はユーザーが明示的に変更する。

==================================================
15. SKIP Conditions
==================================================

例：

- conservative EV below threshold
- Probability ModelとRanking Modelの乖離大
- 必要な当日情報不足
- scratch / jockey change後の再計算未完了
- Odds変動が大きすぎる
- 高EVが不安定な単一Featureに依存
- capital limit到達
- 100円Minimumでは適切なSizing不能

SKIP Reasonを構造化して保存する。

16. Evaluation
==================================================

Prediction QualityとBetting Qualityを分離評価する。

Prediction：

- Log Loss
- Brier Score
- Calibration
- ranking quality
- その他必要な確率評価

Betting：

- hit rate
- ROI
- max drawdown / loss
- max losing streak
- number of bets
- bet type performance
- strategy performance
- month stability
- course
- distance
- track condition

同じPrediction Snapshotに対して、

- 1/8 Kelly
- 1/4 Kelly
- fixed stake
- strategy variants
- SKIP threshold variants

等を再評価可能にする。

Predictionを再学習しなくても
Betting Logicを比較できる構造にする。
